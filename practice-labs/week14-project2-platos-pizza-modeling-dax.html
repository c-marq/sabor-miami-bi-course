Phase 2 · Fix the Date Column — It's UK Format ⏱ 7 min
💡 WHY — A NEW TWIST ON AN OLD LESSON In Project 1 you dealt with two different date formats mixed in the same column. Plato's Pizza is simpler: just one format. But that format is DD/MM/YYYY (UK/European), not MM/DD/YYYY (US). If you just click Data Type → Date, Power BI will apply your machine's default locale — which is probably English (United States) — and mis-read every date where the day is greater than 12. Half your data would silently become wrong dates with no error message.

The fix is Using Locale, same tool you used in Project 1, different locale picked.
✅ DO THIS
  1. Click the orders query.
  2. Click the date column header to select it.
  3. Go to Transform tab → Data Type → Using Locale…
  4. In the dialog:
    • Data Type: Date
    • Locale: English (United Kingdom)
  5. You can sample the preview at the bottom of the dialog to confirm the parse looks right. Click OK.
  6. The date column now shows a calendar icon in its header and clean parsed dates like 1/13/2015 (Power BI will display them in your local format, but the underlying values are correct).
⚠️ COMMON MISTAKE Do not use the regular Data Type → Date option — use Using Locale specifically. The regular option will silently apply your machine's default locale and get half the dates wrong.
🛑 STOP AND CHECK The date column in orders should show a calendar icon and real date values. Click the filter dropdown on the column to see the date range — it should span the full year 2015 (January to December), not weird gaps. If you see errors or gaps, your locale was wrong.
Phase 3 · Flatten pizza_types Into pizzas ⏱ 10 min
💡 WHY — THE SHAPE PROBLEM Right now the dimension side of the model is in two tables: pizzas (size, price) and pizza_types (category, name, ingredients). These are linked by pizza_type_id. That is called a snowflake, and Power BI can technically handle it — but a star schema is cleaner. A star schema flattens dimension tables so every pizza row directly carries its category. The way to flatten is a merge in Power Query, which you did four times in Lab #2.

After this phase, pizzas will have a category column directly on it, and pizza_types will no longer load into the model.
✅ DO THIS — merge pizza_types into pizzas
  1. Click the pizzas query.
  2. Home tab → Merge Queries → Merge Queries (not "as new").
  3. In the dialog:
    • Top table: pizzas (already selected)
    • Click the pizza_type_id column in the top preview
    • Bottom table dropdown: pick pizza_types
    • Click the pizza_type_id column in the bottom preview
    • Join Kind: Left Outer (all from first, matching from second)
  4. Click OK. A new column called pizza_types appears at the right end of pizzas, containing nested Table values.
  5. Click the expand icon (two small arrows) on the new column header.
  6. In the expand dialog, uncheck everything, then check only category. Also uncheck Use original column name as prefix. Click OK.
💡 WHY ONLY CATEGORY? pizza_types has four columns: pizza_type_id, name, category, ingredients. For your measures, you only need category — it is what you will use in the CALCULATE filter later. Pulling in name and ingredients would bloat the pizzas table without giving you anything useful for this project. When in doubt: only bring in what you actually need.
✅ DO THIS — disable loading on pizza_types
  1. In the Queries pane, right-click pizza_types.
  2. Uncheck Enable load. The query name should now appear in italics.
⚠️ COMMON MISTAKE Do not Delete pizza_types from the Queries pane. If you delete it, the merge step in pizzas will break. Disable load keeps the query alive for internal use but hides it from the model.
🛑 STOP AND CHECK Click pizzas. You should see the original 4 columns (pizza_id, pizza_type_id, size, price) plus a new category column at the right end. Every row should show one of these 4 values in category: Chicken, Classic, Supreme, or Veggie. If category is blank or missing, your merge failed — check the join keys.
Phase 4 · Compute line_total in order_details ⏱ 12 min
💡 WHY — REVENUE LIVES IN THE FACT TABLE To write DAX measures like "Total Revenue," we need a revenue value we can sum. But the fact table (order_details) only has quantity — the price is in pizzas. We could write a DAX formula that multiplies across tables, but that introduces a new pattern you have not practiced yet. For review week, we keep DAX simple: we compute line_total directly inside order_details using Power Query, so every measure can be a pure SUM — exactly like you wrote in Lab #3.

The trick: merge pizzas into order_details temporarily to pull in price, compute line_total = quantity × price, then drop the price column so order_details stays lean.
✅ DO THIS — temporary merge to pull in price
  1. Click the order_details query.
  2. Home → Merge Queries → Merge Queries.
  3. In the dialog:
    • Top table: order_details
    • Click the pizza_id column in the top preview
    • Bottom table dropdown: pick pizzas
    • Click the pizza_id column in the bottom preview
    • Join Kind: Left Outer
  4. Click OK. A new pizzas column appears at the right end.
  5. Click the expand icon on the new column. Uncheck everything, then check only price. Uncheck the prefix option. Click OK.
✅ DO THIS — add a custom column for line_total
  1. Still on order_details, go to Add Column tab → Custom Column.
  2. New column name: line_total
  3. In the formula box, type (or copy) exactly this:
    = [quantity] * [price]
  4. Click OK. A new line_total column appears at the right end.
  5. If the column type is "ABC123" (any), change it to Decimal Number using the icon at the left of the column header.
✅ DO THIS — drop the price column
  1. Right-click the price column header in order_details → Remove.
  2. Your fact table now has its own revenue (line_total) and does not need price anymore. pizzas still has price — we just do not need it duplicated on every transaction row.
💡 WHY DROP IT? Carrying price on every row of order_details (48,620 rows) when it really belongs in pizzas (96 rows) is wasteful. line_total is different — it is the result of a calculation that needs to live at the row level. That one is earning its place in the fact table. price is not.
🛑 STOP AND CHECK order_details should now have these columns: order_details_id, order_id, pizza_id, quantity, line_total. That is it. No price column. Row count still around 48,620. Click on any row and mentally check: does line_total look like quantity × a reasonable pizza price? For a quantity of 1 the value should be somewhere between $9 and $36.

💡 WHY MODEL VIEW MATTERS Model View is where relationships live. A relationship tells Power BI: "when someone filters pizzas by category, the filter should travel through to order_details automatically." Without relationships, your measures cannot respond to slicers or filters correctly. This is the piece Lab #3's starter file gave you for free. In Project 2 you build it yourself.
✅ DO THIS — open Model View
  1. On the left sidebar of the main Power BI window, click the Model view icon (third icon from the top — looks like two connected rectangles).
  2. You should see three boxes on the canvas, one for each table: order_details, orders, pizzas.
  3. Arrange them so order_details is in the middle and orders and pizzas are on either side. Drag the headers to reposition.
✅ DO THIS — check for auto-detected relationships Power BI may have auto-detected relationships when you loaded the data. Look at the canvas:
  • If there is a line connecting order_details[order_id] to orders[order_id], good.
  • If there is a line connecting order_details[pizza_id] to pizzas[pizza_id], good.
  • If both lines already exist, skip ahead to the STOP AND CHECK.
  • If either is missing, follow the steps below to create them manually.
✅ DO THIS — manually create any missing relationships
  1. Home tab → Manage Relationships → New.
  2. For the order_details ↔ orders relationship:
    • Top table: order_details, column order_id
    • Bottom table: orders, column order_id
    • Cardinality: Many to one (*:1)
    • Cross filter direction: Single
    • Check Make this relationship active
    • Click OK
  3. Repeat for order_details ↔ pizzas:
    • Top table: order_details, column pizza_id
    • Bottom table: pizzas, column pizza_id
    • Cardinality: Many to one (*:1)
    • Cross filter direction: Single
    • Active: Yes
    • Click OK, then Close
🛑 STOP AND CHECK Your Model view should now show:
  • A line from order_details to orders with a * on the order_details side and a 1 on the orders side
  • A line from order_details to pizzas with a * on the order_details side and a 1 on the pizzas side
  • An arrow on each line pointing from the 1-side (dimension) to the *-side (fact)
If the lines exist but the cardinality is backwards or the filter direction is "Both," double-click the line and fix it. The * always belongs on the fact table side.
Phase 8 · Create the Date Table ⏱ 12 min
💡 WHY A SEPARATE DATE TABLE? You already have a date column in orders. Why create a whole separate Date table? Three reasons:
  • A Date table has one row per day, even on days with zero orders — that keeps your time analysis honest.
  • A Date table has calendar columns (Year, Month, Quarter) ready to drag into visuals without extra work.
  • Time intelligence DAX functions (like TOTALYTD) require a proper Date table with every date present.
You built one of these in Week 12. This is the same pattern.
✅ DO THIS — create the Date table using a DAX formula
  1. On the left sidebar, click the Table view icon (second icon — looks like a data grid).
  2. On the Home tab (or Modeling tab depending on view), click New table.
  3. A formula bar appears at the top. Delete whatever is there and paste this formula exactly:
Date =
ADDCOLUMNS (
    CALENDAR ( DATE ( 2015, 1, 1 ), DATE ( 2015, 12, 31 ) ),
    "Year", YEAR ( [Date] ),
    "Month Number", MONTH ( [Date] ),
    "Month Name", FORMAT ( [Date], "mmmm" ),
    "Quarter", "Q" & QUARTER ( [Date] ),
    "Day Number", WEEKDAY ( [Date] ),
    "Day of Week", FORMAT ( [Date], "dddd" )
)
✅ DO THIS — continue
  1. Press Enter or click the checkmark to confirm the formula.
  2. A new table called Date appears in your Data pane. It should have 365 rows (one per day in 2015) and 7 columns.
💡 WHAT THIS FORMULA DOES CALENDAR creates a table with one column, [Date], filled with every day from Jan 1, 2015 through Dec 31, 2015. ADDCOLUMNS wraps around that and adds 6 calendar columns computed from each date. This is the same pattern you used in Week 12 — just with hardcoded 2015 dates matching the Plato's Pizza data range.
✅ DO THIS — mark as Date table
  1. With the Date table selected in the Data pane, click the Table tools tab at the top of Power BI (it appears when a table is selected).
  2. Click Mark as date table.
  3. In the dialog, pick Date as the date column and click OK.
✅ DO THIS — sort Month Name and Day of Week properly By default, "Month Name" sorts alphabetically (April, August, December...) which is wrong. We want chronological (January, February, March...).
  1. In the Data pane, click the Month Name column under the Date table.
  2. Go to Column tools tab at the top → Sort by column → pick Month Number.
  3. Now click the Day of Week column.
  4. Column tools → Sort by column → pick Day Number.
✅ DO THIS — connect Date table to orders
  1. Go back to Model view (left sidebar, third icon).
  2. The Date table should appear as a new box on the canvas.
  3. Drag Date[Date] onto orders[date] to create a relationship.
  4. If a dialog appears, confirm: Many-to-one from orders to Date, single cross-filter direction, active.
🛑 STOP AND CHECK Your Model view should now show 4 tables with 3 relationships forming a clean star:
  • order_details (fact, in the middle) connected to orders and pizzas on both sides
  • orders connected to Date through the date column
  • Every line has a * on the fact/order side and a 1 on the dimension/Date side

Phase 9 · Write Five DAX Measures ⏱ 30 min · Tutoring Block
💡 WELCOME BACK Open your Project 2 file. Your star schema is built, your Date table is live, your relationships are in place. All the plumbing is done. Now you write the 5 measures that prove it works.

Every one of these measures uses DAX patterns you already wrote in Lab #3. You have done all of this before — on Sabor Miami. This is the same work on a new dataset.
✅ DO THIS — how to create a measure For each of the 5 measures below:
  1. Go to Report view (left sidebar, top icon).
  2. In the Data pane on the right, right-click the order_details table → New measure.
  3. Type or paste the measure in the formula bar.
  4. Press Enter or click the checkmark.
  5. Optional but recommended: with the new measure selected, go to Measure tools at the top and set the format (Currency for revenue measures, Whole Number for counts, Decimal with 2 digits for averages).

Measure 1 · Total Revenue

Total Revenue = SUM ( order_details[line_total] )
💡 WHY Same pattern as Lab #3's Total Sales = SUM(sales[amount]). We built line_total in Power Query specifically so this measure could be a simple SUM. Format as Currency.

Measure 2 · Total Orders

Total Orders = DISTINCTCOUNT ( order_details[order_id] )
💡 WHY DISTINCTCOUNT AND NOT COUNT? A single order can have multiple pizzas — so order_id appears multiple times in order_details (once per pizza on that order). COUNT would give you the total number of pizza lines, not the number of orders. DISTINCTCOUNT counts each unique order_id only once. This is the same pattern as Lab #3's Unique Items Sold measure.

Measure 3 · Total Pizzas Sold

Total Pizzas Sold = SUM ( order_details[quantity] )
💡 WHY Each row in order_details represents a pizza on an order, and quantity tells you how many of that pizza were ordered. Summing quantity across all rows gives total pizzas sold. Pure SUM, same pattern as Lab #3.

Measure 4 · Average Order Value

Average Order Value = DIVIDE ( [Total Revenue], [Total Orders] )
💡 A MEASURE THAT USES MEASURES Notice this measure calls other measures — [Total Revenue] and [Total Orders]. You do this by typing the square brackets and Power BI will autocomplete. This pattern is powerful: once you define a measure, you can reuse it inside other measures. DIVIDE is also the same safe-division function you used in Lab #3 for Tip Percentage. Format as Currency.

Measure 5 · Classic Category Revenue (the CALCULATE)

Classic Category Revenue =
CALCULATE (
    [Total Revenue],
    pizzas[category] = "Classic"
)
💡 THIS IS THE SAME THING YOU DID WITH LA HAVANA EXPRESS In Lab #3, you wrote CALCULATE(SUM(sales[amount]), trucks[truck_name] = "La Havana Express"). This is the exact same pattern on a new dataset:
  • The expression is [Total Revenue] (instead of SUM) — using a measure is cleaner than rewriting the SUM
  • The filter is pizzas[category] = "Classic" — filtering the dimension table by a column value, just like filtering trucks by truck_name
This measure will return the revenue only from pizzas in the Classic category, no matter what other filters are applied by visuals or slicers. That is the override behavior of CALCULATE. Format as Currency.
⚠️ COMMON MISTAKE Case matters in the filter string. "Classic" works. "classic" does not match anything because the data has a capital C. If your measure returns 0 instead of a real number, check the capitalization of your filter string against the actual data.
🛑 STOP AND CHECK You should now have 5 measures visible under the order_details table in the Data pane. They should all show the calculator icon (not the column icon). None should show a red error indicator. If any has an error, click it to read the message — usually it is a typo in a column reference.
Phase 10 · Build the Verification Visual ⏱ 15 min
💡 WHY THIS VISUAL The verification visual is a copy of the table you built in Lab #3 to see CALCULATE override filter context. The setup: a table with category on the rows, [Total Revenue] next to it, and [Classic Category Revenue] in another column. When you read the table, you will see:
  • Chicken row: Total Revenue shows Chicken revenue. Classic Category Revenue shows Classic revenue (ignores the Chicken row filter).
  • Classic row: Both columns show the same number (Classic revenue filtering + Classic revenue override land on the same answer).
  • Supreme row: Total Revenue shows Supreme revenue. Classic Category Revenue still shows Classic revenue.
  • Veggie row: Same pattern.
That behavior — the CALCULATE column showing the same number in every row regardless of what the row filter says — is filter context override in action. This is the same thing you saw with La Havana Express Sales in Lab #3.
✅ DO THIS — build the table
  1. Go to Report view.
  2. In the Visualizations pane, click the Table icon (small grid).
  3. A blank table appears on the canvas.
  4. In the Data pane, expand pizzas and drag category into the table's Columns well.
  5. Expand order_details. Drag [Total Revenue] into the Columns well.
  6. Drag [Classic Category Revenue] into the Columns well too.
  7. Resize the visual so all three columns are readable.
🛑 STOP AND CHECK — The Filter Context Override Test Your table should show 4 rows (Chicken, Classic, Supreme, Veggie). The key observation:
  • The Total Revenue column varies row by row — each row shows the revenue for that category.
  • The Classic Category Revenue column shows the same number in every row.
If that is what you see, CALCULATE is overriding the row filter exactly like it is supposed to. If Classic Category Revenue also varies by row, something is wrong with your measure — check that the filter is pizzas[category] = "Classic" and that pizzas has a real category column (Phase 3).
✅ DO THIS — add a revenue-by-category bar chart
  1. Click on blank canvas space (not on the existing table) to deselect.
  2. In the Visualizations pane, click the Clustered bar chart icon.
  3. Drag pizzas[category] into the Y-axis well.
  4. Drag [Total Revenue] into the X-axis well.
  5. Resize the chart so you can see all 4 categories clearly.
💡 THE MEANINGFUL SECOND VISUAL The table proves your CALCULATE works. The bar chart answers a real business question: which pizza category is driving the most revenue at Plato's Pizza? You should see Classic and Supreme as the top categories, Veggie and Chicken smaller. That is how pizza businesses typically shake out.

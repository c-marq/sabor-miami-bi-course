Phase 1 · Create a Date Hierarchy ⏱ 15 min
💡 WHY HIERARCHIES MATTER Right now, if you drag a date field into a visual, you see all the individual dates as a flat list. A hierarchy organizes related columns into a drill-down path — Year → Quarter → Month — so users can start at the top level and click to see more detail. Think of it as a staircase: you walk from year to quarter to month, one step at a time. Chapter 10 calls this "a staircase, not an elevator."
✅ DO THIS — build the hierarchy in Model View
  1. Switch to Model View (left sidebar, third icon — the one that looks like connected boxes).
  2. Find the Date table on the canvas.
  3. Right-click the Year column → Create hierarchy.
  4. A new item called "Year Hierarchy" appears at the bottom of the Date table's column list. Right-click it → Rename → type Date Hierarchy.
  5. Drag Quarter onto the Date Hierarchy item. It becomes Level 2.
  6. Drag Month Name onto the Date Hierarchy item. It becomes Level 3.
🛑 STOP AND CHECK In the Date table, you should see Date Hierarchy with three levels listed beneath it: Year (Level 1), Quarter (Level 2), Month Name (Level 3). If the levels are in the wrong order, right-click a level and use Move Up or Move Down to reorder.
✅ DO THIS — test the drill-down in a visual
  1. Switch to Report View (left sidebar, top icon).
  2. Click an empty area of the canvas.
  3. In the Visualizations pane, click Clustered bar chart.
  4. From the Data pane, expand the Date table. Drag Date Hierarchy to the Y-axis well.
  5. Drag one of your measures (e.g., Total Sales) to the X-axis well.
  6. The chart shows one bar for 2024. Look at the top of the visual for small arrow icons — these are the drill-down controls.
  7. Click the double-arrow icon (Expand all down one level). The single bar splits into 4 quarter bars.
  8. Click the double-arrow again. The 4 quarter bars expand into 12 month bars.
⚠️ COMMON MISTAKE If your months appear alphabetically (April, August, December...) instead of chronologically (January, February, March...), the Sort by Column setting is missing. Go to Table View, click Month Name, then in the Column tools tab, click Sort by column → pick Month Number. You set this up in Week 12 — if it already works, you are good.

Phase 2 · Run Performance Analyzer ⏱ 15 min
💡 WHY PERFORMANCE MATTERS A Power BI report can have dozens of visuals, each running its own query against the data model every time you open the page, click a slicer, or apply a filter. Some visuals load instantly. Some take seconds. Performance Analyzer tells you exactly how long each visual takes to render — so you can find the slow ones and decide what to do about them.

Think of it as a stopwatch for every visual on your report page.
✅ DO THIS — open Performance Analyzer
  1. Make sure you are in Report View and on a report page that has at least 3–4 visuals. If your page only has 1–2, quickly add a couple more: a Card visual with Total Sales, a bar chart by truck_name, a table with a few columns. Performance Analyzer needs multiple visuals to be meaningful.
  2. Click the View tab in the top ribbon.
  3. Click Performance Analyzer. A panel opens on the right side of the screen.
  4. In the Performance Analyzer panel, click Start recording.
  5. Click Refresh visuals. This forces every visual on the page to reload, and Performance Analyzer times each one.
  6. Wait a few seconds for all visuals to finish loading.
  7. Click Stop recording (or just leave it — it will keep recording as you interact).
✅ DO THIS — read the results
  1. The panel shows a list of every visual on the page with timing information. Each visual has a total time in milliseconds (ms).
  2. Click the arrow next to any visual to expand it. You will see a breakdown:
    • DAX query — time spent running the measure calculations
    • Visual display — time spent rendering the visual on screen
    • Other — time spent waiting, processing, or on background tasks
  3. Identify which visual took the longest. This is your "slowest visual."
💡 WHAT THE NUMBERS MEAN For a dataset this size (Sabor Miami has ~500 rows), everything should be fast — probably under 100ms per visual. In real-world models with millions of rows, slow visuals might take 5,000–10,000ms (5–10 seconds). The technique is the same: find the slow one, figure out why, and optimize. Common causes of slow visuals: too many rows in a table visual, complex DAX with nested CALCULATE, or unnecessary columns bloating the model.
🛑 STOP AND CHECK You should be able to identify: (a) which visual was slowest, (b) whether the bottleneck was DAX query time or visual display time. If Performance Analyzer shows nothing, make sure you clicked "Refresh visuals" after starting the recording.

Phase 3 · Remove Unnecessary Columns ⏱ 15 min
💡 WHY REMOVE COLUMNS? Every column in your model takes up space in memory and slows down calculations — even if nobody ever uses it in a visual. Removing columns you do not need makes the model smaller, faster, and easier to navigate. This is called model optimization, and it is one of the first things a BI professional does before publishing a report.

The rule is: if a column is not used in a relationship, a measure, a visual, or a filter — it probably does not need to be in the model.
✅ DO THIS — check the file size before removing columns
  1. Save your file (Ctrl+S).
  2. Open File Explorer and navigate to where your .pbix file is saved.
  3. Right-click the file → Properties. Note the file size (in KB or MB). Write it down — you will compare after removing columns.

File size before:

✅ DO THIS — identify columns that can be removed
  1. Go to Model View.
  2. Look at each table and think: which columns are NOT used in any relationship, measure, visual, or filter?
  3. Good candidates for removal in the Sabor Miami model:
    • employees[phone] — personal contact info, not used in any analysis
    • employees[email] — same reason
    • trucks[license_plate] — operational detail, not analytical
    • events[expected_attendance] — not used in any current measure
    • Date[Day Number] — only used as a Sort By Column for Day of Week. If you are not using Day of Week in any visual, both can go.
⚠️ COMMON MISTAKE — do NOT remove these
  • ID columns used in relationships — if you remove truck_id from sales, the relationship breaks.
  • Columns used in measures — sales[amount] is used in Total Sales. Removing it would break the measure.
  • Sort By Column targets — Month Number is used as the Sort By Column for Month Name. If you remove it, months go back to alphabetical order.
When in doubt, do not remove. You can always remove more later. You cannot easily undo a removal.
✅ DO THIS — remove at least 3 columns
  1. In Model View (or Table View), right-click a column you identified as removable.
  2. Click Hide in report view first. This hides the column from the Data pane in Report View but does not delete it. Check that nothing breaks.
  3. If nothing breaks, you can go further: open Power Query Editor (Home → Transform data), find the column in the relevant query, right-click it → Remove. Then Close & Apply.
  4. Repeat for at least 2 more columns.
💡 HIDE VS REMOVE — TWO LEVELS Hide in report view is the safe option. The column still exists in the model (relationships and measures still work), but report builders cannot see it. Remove in Power Query is the permanent option — the column is gone from the model entirely. For Lab #4, either approach counts. For a professional model, removing in Power Query is the cleaner optimization.
✅ DO THIS — check the file size after
  1. Save the file (Ctrl+S).
  2. Check the file size again in File Explorer → Properties.

File size after:

💡 ABOUT THE SIZE DIFFERENCE On a small dataset like Sabor Miami (~500 rows), the file size difference will be tiny — maybe a few KB. That is normal. On a real-world model with millions of rows, removing unnecessary columns can shrink a file by hundreds of megabytes and cut refresh times by minutes. The skill matters even if the demo is small.
🛑 STOP AND CHECK Open Report View and click through your visuals. Do they all still work? Do your measures still return numbers? If any visual shows an error, you removed a column that was in use — go back to Power Query and undo that step.

Phase 4 · Row-Level Security — Awareness Demo ⏱ 5 min · Instructor-Led
💡 WHAT IS RLS? Row-Level Security (RLS) is a Power BI feature that restricts which rows a user can see. Everyone opens the same report, but each person sees only the data they are authorized to access. In the Sabor Miami model, you might create an RLS role so the manager of La Havana Express (T001) can only see T001's sales — not the sales from Sabor on Wheels, Caribbean Cruiser, or The Plantain Express.

Chapter 10 uses the metaphor: "everyone enters the same house, but some rooms have locks on the doors." The key you hold determines which rooms you can enter.
💡 HOW IT WORKS (YOUR INSTRUCTOR WILL DEMO THIS)
  1. In Power BI Desktop, go to Modeling tab → Manage roles.
  2. Create a role (e.g., "Truck T001 Manager").
  3. Apply a filter on the trucks table: [truck_id] = "T001"
  4. Because of the star schema relationships, this filter flows from trucks through to sales automatically. The user only sees T001's sales.
  5. Test with Modeling → View as → check the role → OK. A yellow banner confirms you are viewing as that role.
You do not need to build this yourself today. Just watch the demo and understand the concept. RLS is not part of Lab #4 — it is a "know that it exists" topic for your certification preparation.
💡 WHY THE FILTER GOES ON THE DIMENSION TABLE Notice the RLS filter is on trucks (the dimension), not on sales (the fact). The star schema's one-to-many relationship carries the filter from dimension to fact automatically. This is the same cross-filter direction you learned in Week 12. The model does the work — you do not need separate filters on every table.

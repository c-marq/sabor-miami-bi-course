Meet the Data: Plato's Pizza

Plato's Pizza has been collecting sales data for a full year (2015). The data is split across 4 tables. Each table holds a piece of the story — and right now, no single table can answer a real business question on its own.

TableRowsColumnsWhat It Contains
order_details48,620order_details_id, order_id, pizza_id, quantityEvery pizza sold — the fact table (like Sales in Sabor Miami)
orders21,350order_id, date, timeWhen each order was placed
pizzas96pizza_id, pizza_type_id, size, priceSize and price for each pizza variant
pizza_types32pizza_type_id, name, category, ingredientsMenu name, category, and ingredients

The tables connect through shared key columns:

order_details.pizza_id → pizzas.pizza_id
order_details.order_id → orders.order_id
pizzas.pizza_type_id → pizza_types.pizza_type_id
💡 WHY ARE WE DOING THIS? Notice the pattern — it is the same structure as Sabor Miami. A fact table (order_details) has foreign key columns that point to dimension tables (pizzas, orders). And one dimension table (pizzas) has its own foreign key pointing to another dimension (pizza_types). Merging connects the pieces so you can answer questions like: "What was the most popular pizza category on Fridays?"

Merge 1 — order_details with pizzas

This merge adds pizza size and price to every order line. It also brings in the pizza_type_id column, which you will use in Part 2 to connect to the pizza menu names.

Key: pizza_id Join: Left Outer Expand: pizza_type_id, size, price
✅ DO THIS — Follow along with your instructor
  1. Click order_details in the Queries pane.
  2. Go to Home tab → Combine section → Merge Queries (the top option, not "as New").
  3. The top table should show order_details.
  4. In the bottom dropdown, select pizzas.
  5. In the order_details preview (top), click pizza_id — it highlights green.
  6. In the pizzas preview (bottom), click pizza_id — it highlights green.
  7. Confirm the Join Kind is Left Outer (all from first, matching from second).
  8. Click OK.
  9. A new column called pizzas appears at the far right. Each cell says "Table."
  10. Click the expand button (↔ icon) on the pizzas column header.
  11. Uncheck "Use original column name as prefix."
  12. Check only: pizza_type_id, size, and price.
  13. Click OK.
🛑 STOP AND CHECK Scroll to the far right of order_details. You should see 3 new columns: pizza_type_id, size, and price. The size column should show values like S, M, L, XL. The price column should show dollar amounts like 12.75 or 20.75.

Why did we expand pizza_type_id? Right now it is just a code like "bbq_ckn." In Part 2, you will use this column to merge with the pizza_types table to get the actual menu name ("The Barbecue Chicken Pizza"). We brought the key across now so you can use it later.

Merge 2 — order_details with orders

This merge adds when each order was placed — the date and time.

Key: order_id Join: Left Outer Expand: date, time
✅ DO THIS — Follow along with your instructor
  1. Make sure order_details is still selected in the Queries pane.
  2. Go to Home tab → Combine section → Merge Queries.
  3. In the bottom dropdown, select orders.
  4. Click order_id in the order_details preview (top) — green.
  5. Click order_id in the orders preview (bottom) — green.
  6. Confirm the Join Kind is Left Outer.
  7. Click OK.
  8. Click the expand button (↔) on the new orders column.
  9. Uncheck "Use original column name as prefix."
  10. Check only: date and time.
  11. Click OK.
🛑 STOP AND CHECK — Both Merges Complete Your order_details table should now have 5 new columns:

✅ pizza_type_id (from pizzas)
✅ size (from pizzas)
✅ price (from pizzas)
✅ date (from orders)
✅ time (from orders)

Check the row count in the bottom-left corner — it should still be 48,620. The Left Outer joins added columns, not rows.
💡 WHY ARE WE DOING THIS? Before these merges, the order_details table only told you "order #2 included pizza bbq_ckn_m, quantity 1." Now it tells you "order #2 included a Medium Barbecue Chicken pizza at $16.75, placed on 01/01/2015 at 11:57 AM." That is the power of merging — turning codes into stories.

Task 1 — Chain Merge: order_details with pizza_types

Here is something new: the pizza_type_id column did not exist in order_details originally. It came from the pizzas table during Merge 1. Now you can use it as a key to merge with a third table — pizza_types — to get the actual menu names and categories. This is called a chain merge: one merge creates the key that enables the next merge.

Key: pizza_type_id Join: Left Outer Expand: name, category
✅ DO THIS
  1. Click order_details in the Queries pane.
  2. Go to Home tab → Combine section → Merge Queries.
  3. In the bottom dropdown, select pizza_types.
  4. In the order_details preview (top), click pizza_type_id — green.
  5. In the pizza_types preview (bottom), click pizza_type_id — green.
  6. Confirm the Join Kind is Left Outer.
  7. Click OK.
  8. Click the expand button (↔) on the new pizza_types column.
  9. Uncheck "Use original column name as prefix."
  10. Check only: name and category.
  11. Click OK.
🛑 STOP AND CHECK Scroll to the far right. You should now see 2 more new columns: name (the full pizza name like "The Barbecue Chicken Pizza") and category (like "Chicken," "Classic," "Supreme," or "Veggie").

Your order_details table now has 7 new columns total from 3 merges. Check the row count — still 48,620.
💡 WHY ARE WE DOING THIS? The chain merge pattern shows up all the time in real data. An e-commerce company might have Orders → Products → Product Categories. A hospital might have Visits → Doctors → Departments. The key from one merge unlocks the next. On Thursday's Lab #2, you will not encounter a chain merge — all three Sabor Miami merges use keys that already exist in the Sales table. But knowing this pattern exists makes you a stronger analyst.
💜 TAKE A BREATH You just completed 3 merges on a dataset you had never seen before today. That means the merge skill is transferring — you are not memorizing steps for one dataset, you are learning a technique that works on any data. Take a moment to stretch before the next task.

Task 2 — Create a Reference Query with Group By

Now you will create a summary table that shows how many pizzas were sold in each category — using a Reference query and Group By, the same technique you will use in Lab #2 Task 4.

✅ DO THIS
  1. Right-click order_details in the Queries pane.
  2. Select Reference. A new query called order_details (2) appears.
  3. Right-click order_details (2) → Rename. Type Sales_ByCategory and press Enter.
  4. With Sales_ByCategory selected, go to Transform tab → Table section → Group By.
  5. In the Group By dialog:
    — Group by: category
    — New column name: Total Quantity
    — Operation: Sum
    — Column: quantity
  6. Click OK.
🛑 STOP AND CHECK Your Sales_ByCategory query should show a small table with 4 rows — one for each pizza category (Chicken, Classic, Supreme, Veggie) — and a Total Quantity column showing how many pizzas of each type were sold across the whole year.

Task 3 — Configure Loading

Troubleshooting

"I do not see the pizza_type_id column in order_details for Task 1."
You may not have expanded it during Merge 1 in Part 1. Go back to the Applied Steps pane, find the "Expanded pizzas" step, and click it. If pizza_type_id is missing, delete this step (click the X) and redo the expand — this time check pizza_type_id, size, and price.

"The name column shows null after the chain merge."
Double-check that you selected pizza_type_id (not pizza_id) in both the top and bottom table previews in the Merge dialog. The pizza_type_id values look like "bbq_ckn" while the pizza_id values look like "bbq_ckn_s" — they are different columns.

"I lost my Part 1 work — my file does not have the first 2 merges."
Ask your tutor for the PlatosPizza_Part2_Starter.pbix backup file, which has Part 1 already completed.

"My Group By only shows 1 row instead of 4."
You may have grouped by the wrong column. Delete the Grouped Rows step and redo it — make sure you select category (not pizza_type_id or pizza_id) in the Group By dropdown.

"Close & Apply is very slow."
The order_details table has 48,620 rows — loading may take 30–60 seconds. This is normal. Wait for the loading bar to finish.
